# v1.2.24 — publish from CI, and prove a packaged install is actually live

Docs, packaging and release-infrastructure release. No lifecycle behaviour changed.

## 1. The npm README had fallen behind

The published 1.2.23 tarball was built before the GUI-install and live-verification sections were
written, so the npm page told a different install story than the repository. npm versions are
immutable, so the only fix was a new release: 1.2.24 republishes the current README (26,128 bytes,
verified present in the published packument).

## 2. Releases no longer need a one-time password

Publishing previously required an interactive passkey approval, and the browser-auth session expires in
about a minute — shorter than a chat round-trip, so three attempts were lost to expiry before the
publish was completed by hand. It also failed once outright when the CLI login token aged out
(`E401`, "You must be logged in to publish packages"), which is the normal fate of a short-lived token.

`.github/workflows/publish.yml` now publishes over OIDC trusted publishing. The package is bound to this
repository and this workflow filename; the npm CLI exchanges the workflow identity for a short-lived
token. `NODE_AUTH_TOKEN` is deliberately absent. Release flow is now:

```sh
# bump package.json (and the three aligned version literals), commit, then:
git tag v<version> && git push origin v<version>
```

The first CI release (`v1.2.24`, run `36329591930`) completed with all gates green — tag/package match,
the full test suite, the packaged-plugin guard, and publish. npm signed a provenance attestation naming
this repository and commit, published to the transparency log
(`https://search.sigstore.dev/?logIndex=2976987587`). That attestation is a stronger statement than the
manual publishes could make: it is a verifiable claim about *where and how* the artifact was built.

Two workflow defects were found and fixed in the same pass: `actions/setup-node@v4` silently ignored the
`package-manager-cache` input (now `v5`), and `workflow_dispatch` gained `dry_run` (default true) so the
pipeline can be rehearsed without consuming a version number.

## 3. CI now guards the defect that shipped in 1.2.22

The `Packaged plugin must not be inert` step packs the tarball, asserts `harness/plugin/_controller.js`
is present, and loads the packaged plugin exactly as OpenCode does — requiring it to register both
tools. This is the 1.2.22 defect (installed, enabled, zero tools) caught automatically instead of by
hand. It passed in CI run `36329766226`.

## 4. Packaged installs confirmed live, not merely loaded

v1.2.23 proved a packaged plugin *loads*: `toolsBuilt: true`, both tools present. It did **not** prove
the harness's own verification would accept it as live. `doctor --live` rejected the load record with
`no-hook-activity`, because `hookActivity` is only incremented when the `longrun` tool actually executes
in the host process.

That is now exercised end-to-end, using the published 1.2.24:

1. An isolated config dir, provider pointing at a local tool-calling model.
2. The plugin added the way the GUI adds it: `opencode plugin opencode-longrun-harness -g`.
3. A long-lived `opencode serve` host, so the process outlives the turn.
4. A real tool call through that host: `opencode run --attach ...` → `⚙ longrun {"action":"help"}`.

Resulting load record: `harnessVersion 1.2.24`, `toolsBuilt true`, `hookActivity 1`, pid alive. The
harness's own verification then reported:

```
cmd=doctor mode=live-readiness status=LIVE_DETECTED live=OBSERVED
  note A live load was observed; still confirm cancellation/compaction legs separately
      before trusting bounded mode.
```

Against the same setup before the tool call, the verdict was `STALE_LOAD_RECORD` / `NOT_VERIFIED`
(`no-hook-activity`). Loading and *having been used* are different claims, and the harness distinguishes
them.

## Limits

- **A GUI-only install has no release directory**, so the install-check `longrun-harness doctor` reports
  `not installed` for it — the operator CLI needs the tree that `longrun-harness install` writes.
  `doctor --live` evaluates load records but still needs a resolvable controller to run at all.
- In the run above the doctor was executed from the 1.2.22 installed tree while reading a 1.2.24 load
  record, so it also reported `DEGRADED release pointer / executed controller / installer version
  mismatch`. That is an artifact of the test harness, not a packaged-install defect; the live verdict is
  what was under test.
- The `--attach` run used a local `qwen-local` endpoint rather than the commissioning model, purely to
  make the host invoke the tool. The model is incidental to the claim: `hookActivity` measures that the
  plugin's own tool executed in a real host, not which model asked for it.
- Trusted publishing moves the trust boundary: anyone with write access to this GitHub repository can
  publish. The workflow is the only entry point, and provenance records which commit built the release.
- `npm publish --dry-run` fails on a version that already exists, so a `dry_run` rehearsal after a
  release reports that conflict. Rehearsing before tagging is the intended use.
