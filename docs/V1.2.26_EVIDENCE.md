# v1.2.26 — an operator `version` command, and load-record hygiene

Two operational fixes. No lifecycle behaviour changed.

## 1. OpenCode cannot tell you a plugin's version, so the harness now can

Asking "which plugins are installed, and at what version?" had no simple answer. OpenCode records a
plugin as a bare path or npm spec and stores no version for it, so `opencode debug info` lists *what*
is loaded but never *which version*. For the harness, the version lives in its release pointer, and the
only way to read it was to know that and go looking.

`longrun version` now answers it, and installs as the `/longrun-version` command:

```
long-run harness 1.2.26
config dir: /Users/seanj/.config/opencode
installed plugins (2):
  mtplx-session-headers.js  not declared
  longrun.js                1.2.26  (long-run harness)
```

Two things make it correct rather than approximately correct:

- **It reads the `plugins/` directory as well as the config array.** OpenCode auto-loads every file in
  `plugins/` — the convention this installer uses — so the harness plugin appears in *no* config array.
  Reading the config alone omits the harness itself, which is exactly what the first implementation did
  until a test caught it.
- **It is handled before controller resolution.** `version` is pure file inspection, so it works where
  the release tree is absent, such as a GUI-only npm install where the install-check `doctor` reports
  "not installed". A test pins that.

The shipped command pins `agent: build`, for the same reason the read-only guard exists: a version
question asked from inside the `longrun` agent is the shape of request that once produced a stray
tracked run against a months-old commissioning fixture.

## 2. Load records accumulated forever

`doctor --live` prints one rejection line per load record, and every short-lived host instance leaves
one behind. One real state directory had reached **121 records, all but three with dead pids**, so the
verdict was buried under a hundred lines of long-dead processes. The earlier manual prune that cleared
that directory was cosmetic — records were back within the hour.

Both halves are fixed:

- **The plugin prunes on write.** After writing its own record, it deletes records whose pid is no
  longer alive. A dead-pid record can never satisfy the live check, and a live record for another host
  is left alone. It is conservative: anything unparseable, or without a numeric pid, is kept.
- **`doctor --live` summarises by reason.** The text output is now one line —
  `5 load record(s) rejected as untrusted: 4 dead-or-missing-pid, 1 stale` — instead of one per record.

The machine-readable detail is deliberately untouched: `liveEvidence.rejectedUntrusted` still carries
one entry per record with its reason, and `liveEvidence.rejectionSummary` adds the counts. A test
asserts both, so shortening the text can never silently drop evidence.

## Regression

**297** harness regressions pass (292 prior + 5 new):
`harness/test/v1226-version-and-retention.test.mjs`. The new tests cover plugin discovery from both the
config array and the auto-loaded directory, JSONC with comments and trailing commas, absolute-path
entries, version resolution from the release pointer and from a file literal, `version` working with no
release tree, the installed command carrying a baked launcher path with no placeholder left, the
retention rule (prunes dead, keeps live, never deletes a non-record file), and the doctor summary
keeping per-record detail in JSON.

The retention test runs in a child process with `OPENCODE_CLIENT=1` and the test context disarmed,
because the prune only executes in a host process — a test-context import must write nothing.

## Limits

- **A slash command still costs one model turn.** OpenCode commands *are* prompts; there is no way to
  make one print text without the model replying. The command injects the shell output so the model has
  nothing to compute, but a turn is still spent. The same information is available with no model at all
  from `longrun version` or `longrun-version` in a shell.
- **Version resolution is honest about what it cannot know.** An npm-spec plugin resolves from
  OpenCode's package cache; if it is not cached yet, or a file declares no version, the answer is
  `not declared` rather than a guess.
- **Pruning is best-effort** and runs only in a host process. It is not a guarantee that the directory
  is bounded if records are written by processes that never load the plugin again.
- Offline tests plus one real-host confirmation of each fix; not a broad field trial.
