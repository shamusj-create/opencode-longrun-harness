# v1.2.23 — packaged installs: the plugin resolved no controller and went inert

## Defect and reproduction

The plugin resolves its controller from an ordered candidate list:

1. `LONGRUN_CONTROLLER_FILE` (test/override),
2. the install-time baked `file://` URL,
3. the sibling `./_controller.js` next to the plugin.

`longrun-harness install` satisfies (2): it substitutes `__LONGRUN_CONTROLLER_URL__` with an absolute
path into the copy it writes to `<config>/plugins/longrun.js`. When OpenCode instead resolves the
**npm package** — the Desktop Plugins pane, or `opencode plugin opencode-longrun-harness -g` — nothing
bakes anything, and the package shipped no sibling for (3). `loadController()` therefore returned
`null`, and `server()` took its inert branch:

```js
if (!C || isDisabledGlobally()) return {};
```

The result is the worst available failure mode: the plugin installs, the config entry is written, the
harness reports success — and the plugin registers **zero tools** with a single warn-level log line.
Nothing fails; the tools simply never exist.

Reproduced against the **published** 1.2.22 tarball, loaded exactly as OpenCode loads an npm plugin:

| Loaded entry | tools registered | log | load records |
| --- | --- | --- | --- |
| published `opencode-longrun-harness@1.2.22` | **0** | `controller NOT found; plugin inert` | 0 |
| packaged `1.2.23` | **2** — `longrun`, `longrun_verify` | `loaded` | 1 |

Both runs import the package entry directly with `OPENCODE_CLIENT=1`, an isolated
`LONGRUN_STATE_DIR`, and **no** `LONGRUN_CONTROLLER_FILE`, so the only difference is the shipped file.

## Fix

`harness/plugin/_controller.js` ships in the package as a location-independent re-export:

```js
export * from "../src/controller.js";
```

That is candidate (3), which the plugin already looked for — the defect was that the package never
provided it. The packaged controller and its `./evidence.mjs`, `./memory.mjs` and `./execution.mjs`
siblings all live under `harness/src`, which is in the published file set, so the relative re-export
resolves wherever the package is unpacked. No absolute path is baked into the package.

The directory-convention install is deliberately unchanged: the installer writes an explicit file list
and only `plugins/longrun.js`, and its baked URL still wins as candidate (2). The shim must never be
copied into `plugins/`, because OpenCode loads every file in that directory and the shim is not a valid
plugin export — it would throw `Plugin export is not a function`. A test pins that.

## Regression

**292** harness regressions pass (287 prior + 5 new), 0 fail:
`harness/test/v1223-package-install.test.mjs`. The new tests cover the shipped shim and its states, the
package layout registering both native tools, a negative control proving the entry alone is inert, the
shim not being a plugin entry, and the installer still baking `plugins/longrun.js` without copying the
shim into the scanned directory.

The pre-existing plugin tests set `LONGRUN_CONTROLLER_FILE` process-wide, which is precisely what hid
this: the override satisfied candidate (1), so the sibling path was never exercised.

## Version alignment

The release version moved to `1.2.23` in all four pinned locations (package.json, controller
`LIFECYCLE_SCHEMA_VERSION`, installer `VERSION`, plugin `VERSION`), which
`v121-commissioning.test.mjs` enforces as a single source of truth. `LIFECYCLE_SCHEMA_VERSION` gates
install consistency only: persisted state carries its own independent schema markers
(`schemaVersion: 1`, `SOURCE_FINGERPRINT_SCHEMA`, `AMENDMENT_SCHEMA_VERSION`), so existing runs are not
invalidated by this bump.

## Package contents

The three dated `docs/V1.2.2x_EVIDENCE.md` release reports were **removed from the published file set**
in this release. They name commissioning projects by name (Godot, annotations, turret), and the harness
is meant to be project-agnostic; they remain in the repository as the release history the README links.
No source, tool, fixture or plugin file references a specific project.

## Limits

- This makes a packaged install *functional*; it does not make it *complete*. The npm package provides
  the plugin and its two native tools. The agent, slash commands and skills are written by
  `longrun-harness install` into the OpenCode config directory and are not deliverable through the
  plugin mechanism, so a GUI-only install is a subset of a full install.
- Offline tests and a faithful loader simulation, not evidence from a running OpenCode host. The
  end-to-end check is the published package installed through the real plugin installer.
